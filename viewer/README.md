# DW-S1-08/09 — Offline 3D viewer + in-viewer measurement

Static, offline viewer for `pipeline_to_3d_v1` `.glb` output. No CDN, no network calls at
runtime — everything it loads is vendored or local.

#### Run it

**Supported Python versions: 3.12.x and 3.14.x.** The launcher checks this
explicitly and refuses to start with a clear message on any other version.
3.14.6 is the interpreter the full pipeline's recorded evidence was produced on
(and a real `/api/upload` was re-verified under it on 2026-09-29); 3.12 is the
isolated demo-fallback venv. 3.10 and 3.11 both hit hard, independent
dependency-version walls on packages the *full* pipeline depends on.

Real uploads run `run_pipeline.py` in a subprocess with this same interpreter, so
that interpreter needs the full root `requirements.txt` stack (torch cu129 etc.),
and `checkpoints/da2_small_finetuned_v3_full_encoder_ema.pt` must hash to
`a1e3fca3...9ea7` (v3, the runner default) -- `run_pipeline.py` refuses any other file (set
`DW_CHECKPOINT` + `DW_CHECKPOINT_SHA256` only for a deliberately different one; the B0
rollback is `da2_small_finetuned_iter2_partial_unfreeze.pt`, `74ccde40...78d8`).

**Minimal viewer/A2 startup** (mesh viewing, height/measurement, reference-DSM
comparison) needs only two packages:

```bash
pip install -r viewer/requirements.txt
```

**Run this from the repository root** (not from inside `viewer/`):

```bash
python viewer/server.py
```

Then open `http://localhost:8793/`. This single command serves the viewer itself
*and* the P0-A2/A3 APIs (reference-DSM comparison, real image upload) from one
process — it replaced the older static-only `python -m http.server` one-liner,
which only served files and had no backend for those two features.

If a required Python version or the two minimal startup packages above are
missing, the launcher now prints a clear, actionable message and exits --
never a raw traceback (fixed 2026-09-14, after a genuine clean-checkout
failure found during non-author testing; see issue #40 for the full
evidence trail).

## What's here

- `index.html` / `main.js` — scene, camera, renderer, HUD. Uses an import map (`"three":
  "./vendor/three.module.js"`) so nothing resolves to a package manager or CDN at runtime.
- `vendor/` — three.js **0.160.0**, vendored as ES modules, mirroring the real
  `three/examples/jsm` directory layout so their relative imports resolve without edits:
  - `vendor/three.module.js` — core library
  - `vendor/loaders/GLTFLoader.js` — loads the pipeline's `.glb`
  - `vendor/controls/OrbitControls.js` — orbit navigation
  - `vendor/utils/BufferGeometryUtils.js` — `GLTFLoader`'s one relative dependency
  (0.160.0 chosen to match the version already validated against real pipeline output in
  `PHASE2_RED_FLAGS/outputs/metrics/K4_viewer_browser_test.json` — not a new, unvalidated pin.)
- `placeholder_relative.glb` — a small synthetic heightfield mesh (64x64, ~175 KB),
  generated by `make_placeholder_glb.py` using the **real** `heightfield_to_mesh()` from
  `PHASE2_RED_FLAGS/scripts/heightfield_lib.py` (the frozen `pipeline_to_3d_v1` producing
  function) against synthetic elevation/RGB arrays. Only the input data is fake; the mesh
  is built by the actual pipeline function, so nothing about the viewer's loading path needs
  to change once real `run_pipeline.py` output (DW-S1-07, #24) is loaded via `?glb=`.
- `placeholder_relative.glb`'s sidecar, written by the same script so they stay in sync -
  the **frozen `viewer_input_v1` contract** (issues #26/#27, IF-1), the same schema
  `run_pipeline.py` itself emits for real output:
  - `placeholder_relative_elevation.f32` — the raw elevation grid as little-endian float32
    bytes (row-major, `H*W*4` bytes) - a browser can't parse `.npy`, and a nested JSON array
    does not scale past a placeholder-sized tile, so this is what `main.js` actually reads.
  - `placeholder_relative_surface_meta.json` — `schema`, `branch: "relative"`,
    `pseudo_gsd`/`gsd`, `z_exaggeration`, grid shape, `crs`, mesh/LOD references,
    `is_placeholder: true`, and the explicit mesh-frame formula. See
    `run_pipeline.write_surface_meta()`'s docstring for the full field-by-field contract.
  - **Filename convention**: a mesh's sidecar shares its own filename stem with a trailing
    `_lod` stripped (`{stem}.glb` / `{stem}_lod.glb` -> `{stem}_surface_meta.json` /
    `{stem}_elevation.f32`) - `main.js` derives the sidecar path directly from whichever
    `.glb` URL it was given (`viewer/sidecar.js`), so a mesh and its own sidecar can never
    be mismatched with another mesh's data, even when relative and metric outputs from the
    same run sit in the same directory.
- `make_placeholder_glb.py` — regenerate all of the above if needed: `python
  viewer/make_placeholder_glb.py`.

## Navigation

- **Orbit** (default): drag to rotate, scroll to zoom.
- **Fly** (press `F` to toggle): WASD to move, drag to look, Q/E for down/up. This is the
  Day-2 stub the issue asks for — a real fly-camera refinement is Aishee's Day-3 half of #26.

## Measurement (DW-S1-09, #27) — gated on a valid sidecar (DW-WP2, IF-1)

`M` and click-to-pick only do anything when the currently loaded mesh has a sidecar that
passes `sidecar.js::validateSurfaceMeta()`. Missing/invalid metadata, an unsupported
schema, or invalid payload dimensions/type disables both, and a visible banner explains
why (top of screen, red) — the viewer never falls through to a placeholder or a
previously-loaded mesh's data. This is IF-1's explicit failure contract, not an
incidental limitation.

- **Height-on-click**: click anywhere on the surface for a height readout, top-right. Works via
  three.js raycasting against the loaded mesh, then inverting the hit point back to `(row, col)`
  and bilinearly sampling the sidecar's `elevation.f32` at that fractional position — so the
  number shown is a real lookup against the source raster, not read off the (coarser,
  per-vertex) mesh geometry. The unit label is read from the loaded sidecar's own `branch`:
  `"relative units"` with an "uncalibrated surface" warning on the relative branch, `"m"` on
  the metric branch — never a fake metre value on a surface that was never calibrated.
- **Two-point measurement**: press `M` to enter measure mode, then click two points. Horizontal
  distance is `gsd` (real metres/px) on the metric branch, or `pseudo_gsd` (a 1-mesh-unit-per-
  pixel display convention, explicitly NOT metres) on the relative branch — labelled
  accordingly (`sidecar.js::resolveHorizontalScale()`); Δheight and slope follow the same
  branch's unit. **Correction**: an earlier version of this viewer always printed horizontal
  distance in "m" regardless of branch, and always labelled Δheight "relative units" even on
  the metric branch where it is real metres — both were real bugs, fixed as part of DW-WP2.
  Also shows a real elevation-profile line plot (40 bilinearly-sampled points along the
  straight line between the two picks, rendered to an inline canvas). Press `M` again to exit,
  or click two new points to start the next measurement.

## Correctness evidence (DW-S1-09)

Clicked a point in the browser, logged its computed `(row, col)`, then independently
recomputed the bilinear interpolation in Python against `elev.npy` for that exact
`(row, col)`: **both gave `2.974427330251273`, abs diff `0.0`** — the readout provably matches
the source raster, not just "looks about right."

## Day-2 checkpoint evidence

- Loaded with the browser's network disabled (DevTools "offline"): renders correctly, HUD
  shows a real load time and triangle count, 0 console errors.
- `grep -rn "unpkg\|cdn\|https\?://" viewer/index.html viewer/main.js viewer/sidecar.js
  viewer/make_placeholder_glb.py` — **0 matches**. (The vendored `three.js`/`GLTFLoader.js`
  files themselves contain `https://` strings in code comments — spec links, doc references
  — but none are runtime network calls; confirmed via the browser's own network log showing
  every request resolving to `localhost`. `main.js`'s and `sidecar.js`'s own `fetch(...)`
  calls are all relative paths against the same origin the page was served from - DW-WP2's
  sidecar fetches included, since they resolve against whichever `.glb` URL was given.)
- Confirmed via the browser's Network panel: every request (`index.html`, `main.js`, the four
  vendored files, `placeholder.glb`, plus one internal `blob:` URL for the decoded texture)
  resolves to `localhost:<port>` — nothing external.
